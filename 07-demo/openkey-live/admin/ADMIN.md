작성: 2026-11-12 / B(관리자 콘솔). 상태: **1단계 완료 — 모의 서버로만 시험함. 실제 서버(A의 `server.py`) 연결은 미시험.**
기준: [SCHEMA.md](../SCHEMA.md) 5절(실시간 API 계약), 참고: A의 [API.md](../API.md)(작업 중간에 생겨 읽고 맞춤).

## 1. 누구를 위한 화면인가

시연·시험을 **운영하는 사람**(팀원·매장 직원·복지관 강사)이 보는 화면이다. 주인공은 안내만 듣고 혼자 주문을 끝내는 사용자이고, 콘솔은 그 사용자가 지금 어디까지 왔는지, 안내가 무엇을 말했는지 곁에서 확인하고 돕기 위한 것이다. 발표 때 심사위원도 본다.

- 화면 중심은 **주문 진행(메뉴 → 옵션 → 확인 → 결제 → 주문 번호)과 지금 나간 안내 문구**다. 카메라 영상은 옆에서 뒷받침한다.
- 항상 보이는 문구: 머리줄 오른쪽 **"영상은 저장하지 않습니다 · 좌표와 시간만 기록"**, `button_source`가 `kiosk_ground_truth`면 **"버튼 위치: 시연용 정답 좌표 사용"**.
- 기록 구분(`data_source`)을 머리줄에 표시한다. 모의 서버에서는 "예시 데이터 (합성)" 또는 "모의 서버 예시 데이터"가 보인다.

## 3. 화면 구성

창 크기에 따라 두 가지로 배치한다. 둘 다 페이지 스크롤 없이 핵심(영상·안내 문구·단계·시작/종료)이 보인다. 지난 시도 목록만 칸 안에서 스크롤한다.

- **가로 화면**(1366×768, 1536×864, 1920×1080): 왼쪽 영상·인식 상태 / 가운데 주문 진행·지금 안내·요약 / 오른쪽 시험 운영·지난 시도.
- **세로로 긴 반쪽 화면**(1920×1080의 왼쪽 절반 960×1080): 위에 주문 진행, 왼쪽 지금 안내·요약·시험 운영, 오른쪽 영상·인식 상태, 아래 지난 시도.
- 폭 760px 미만은 한 줄로 쌓고 스크롤을 허용한다(휴대폰으로 콘솔을 볼 때 대비, 캡처 확인은 안 함).

| 칸 | 내용 |
| --- | --- |
| 주문 진행 | 목표(주문 내용), 5단계 `steps`(완료/지금/남음), 경과 시간, 키오스크 화면·배치·목표 버튼. 주문 번호 화면이면 "주문을 마쳤습니다 · 주문 번호 N". 시도가 끝난 뒤에는 "직전 시도 · …"(30초 동안은 5단계를 완료로 유지 — 서버가 주문 번호에서 스스로 시도를 끝내도 완료 순간이 보이게) |
| 지금 안내 | 최근 안내 문구를 크게, 이전 문구는 흐리게(시도 시작부터 지난 초). "누르기 안내 가능/보류 · 이유"(`safety`), 다시 듣기·멈춤/재개 버튼, "안내 멈춤 중"·"자동 누름 켜짐 (시연 보조)" 표시 |
| 이번 시도 요약 | `counts`: 누름, 다른 버튼 누름, 되돌림, 망설임, 손 놓침, 손 내림 요청, 안내 횟수와 최근 누름 결과. 평가처럼 보이지 않게 같은 크기·같은 색으로 나열("막힌 곳을 찾기 위한 숫자") |
| 손끝과 목표 버튼 | 카메라 영상(위치 맞춤이 되면 키오스크 부분만 확대) 위에 목표 버튼(파란 틀), 손끝(흰 점), 안내 방향 화살표. 보기 방식: 자동 / 키오스크 / 전체 영상(마커 윤곽 포함) / 도식. 영상이 없으면 키오스크 정규 좌표 도식(`kiosk.regions` 윤곽 + 목표 + 손끝)으로 자동 전환. 손을 놓치면 "마지막으로 본 손끝"을 점선 원으로 |
| 인식 상태 | 카메라, 마커 n/4·맞춤, 손 인식률, 프레임 지연, 모델 시간, 초당 장수, 키오스크, 휴대폰(API.md의 `phone`). 문제가 있을 때만 색을 넣고 맨 위에 할 일 한 줄(예: "마커가 2개만 보입니다 — 휴대폰을 조금 뒤로 옮겨 네 모서리가 모두 보이게 해 주세요") |
| 시험 운영 | 대기 중: 기록 구분, 주문 목표, 배치 A/B, 음성 안내 있음/없음, 안대 예/아니오/모름, 참가자 코드(이름 대신 P01 같은 코드 — 한글이 들어가면 시작을 막음), 조명 메모, 운영 메모, 시도 시작. 진행 중: 조건 요약, 목표 변경, 시도 종료(주문 번호 전이면 "중단으로 기록할까요?" 확인) |
| 지난 시도 | `/api/attempts` 목록(시작 시각·참가자 코드·조건·목표·결과·시간·기록 구분·시도 ID)과 내려받기: JSONL, CSV, JSON(JSONL을 배열 JSON 한 파일로 바꿔 저장) |

서버와 연결이 끊기면 머리줄이 "서버 연결 끊김 · n초 전 상태 표시 중"으로 바뀌고, 아래에 붉은 안내 줄이 나오며, 실시간 칸은 흐려지고 조작 버튼은 잠긴다. 다시 연결되면 저절로 이어진다.

## 4. 조작

| 조작 | 방법 |
| --- | --- |
| 시도 시작 | 조건 입력 후 "시도 시작" 또는 <kbd>Ctrl</kbd>+<kbd>Enter</kbd> → `POST /api/attempt/start {conditions, goal_id, data_source}` |
| 시도 종료 | "시도 종료". 주문 번호까지 끝났으면 바로 `reason:"done"`, 아니면 확인 후 `reason:"aborted"`. 확인 창은 <kbd>Esc</kbd>로 닫음(계속 진행) |
| 다시 듣기 | 버튼 또는 <kbd>R</kbd> → `POST /api/control {action:"repeat"}` |
| 멈춤 / 재개 | 버튼 또는 <kbd>P</kbd> → `{action:"stop"}` / `{action:"resume"}` |
| 목표 변경 | 대기 중에는 주문 목표 선택, 진행 중에는 "주문 목표 변경" → `POST /api/goal {goal_id}` |
| 기록 내려받기 | 지난 시도의 JSONL / CSV / JSON |

키보드 단축키는 입력칸에 글자를 쓰는 중에는 동작하지 않는다(Ctrl+Enter 제외). 모든 버튼·입력에 포커스 테두리가 보인다. 기록 구분·배치 등 마지막 입력값과 보기 방식은 이 브라우저의 `localStorage`에만 기억한다(운영 메모는 기억하지 않음).

## 5. 계약에서 가정한 것

SCHEMA 5절 필드 이름은 바꾸지 않았다. 계약이 정하지 않은 부분은 아래처럼 가정했고, 두 가지 형식을 다 받게 만들었다.

1. `GET /api/events` 응답: 배열 또는 `{events: [...]}`(A의 API.md는 `{attempt, events, last_seq}`). `attempt`가 현재 시도와 다르면 버린다. 시도가 바뀌면 `after=0`부터 다시 받는다.
2. `GET /api/goals`, `GET /api/attempts`: 배열 또는 `{goals: [...]}`·`{attempts: [...]}`. 목표 기본값은 `current` → `default:true` 순.
3. 지난 시도 요약의 조건은 `conditions{…}` 또는 최상위 `layout`·`guidance`(API.md 형식). `goal`은 문자열 ID 또는 `{id,label}`. 내려받기 주소는 `url_jsonl`·`url_csv`가 있으면 그것, 없으면 `/api/attempts/<id>.jsonl|.csv`.
4. `X-Info`의 `H`는 finger-demo와 같이 **카메라 픽셀 → 키오스크 정규 좌표** 3×3(API.md에서 확인). `H`가 없으면 영상만 보이고 겹쳐 그리지 않는다.
5. `/api/frame/latest`가 204면 다시 요청, 404·501이면 "서버가 영상을 주지 않음"으로 보고 5초마다 다시 확인하며 도식으로 표시. 3초 넘게 새 프레임이 없으면 도식으로 전환.
6. 키오스크 화면 비율은 `kiosk.size`·`kiosk.w/h`·`kiosk.aspect`가 있으면 쓰고, 없으면 MORU 키오스크 논리 해상도 1080×1920(9:16)으로 본다(도식 보기에만 쓰임).
7. 안내 기록은 `/api/live`의 `guide`와 `/api/events`의 `guide` 기록(억제된 것 제외)을 합친다. 같은 코드·문구이고 `ms` 차이가 0.4초 안이면 같은 안내로 본다.
8. 주문 번호는 `/api/live`의 `order_no`(모의 서버가 더한 값) → `attempt_end.order_no` → `last_attempt.order_no` → `DONE` 안내 문구의 숫자 순으로 찾는다.
9. 손끝은 `finger.tracked === true`이고 `age_ms`가 0.8초 이하일 때만 "지금 위치"로 그린다.
10. 안내 방향 화살표는 `guide.direction`, 없으면 `guide.code`(LEFT/RIGHT/UP/DOWN, `_SMALL`이면 짧게)로 그린다.
11. 문제 기준(AI 제안값, 실측으로 조정 필요): 손 인식률 60% 미만(시도 중), 프레임 지연 500ms 초과, 모델 시간 120ms 초과, 초당 6장 미만.

## 7. 알려진 한계

- **실제 서버·실제 휴대폰·실제 사용자 미시험.** A의 테스트 서버(8462)에 `GET /api/live`를 한 번 읽어 필드 모양이 API.md와 같은 것만 확인했다(조작 없음).
- 캡처·시험은 모두 모의 서버의 합성 데이터다. 모의 서버의 손 움직임·안내 순서는 그럴듯하게 흉내 낸 것일 뿐 엔진의 실제 동작이 아니다.
- 모의 서버는 시도가 주문 번호에 도달해도 스스로 끝내지 않는다(운영자가 종료). A의 서버는 스스로 `done`으로 끝낸다 — 콘솔은 `last_attempt`와 직전 상태로 완료 표시를 30초 유지하도록 만들었지만 실제 서버에서는 미확인.
- 자동 누름(`auto_click`)은 표시만 하고 켜고 끄는 버튼은 넣지 않았다(시연 보조 기능을 운영 화면에서 쉽게 켜면 "본인이 누른다"는 원칙이 흐려질 수 있어 PM 결정 필요).
- API.md의 `POST /api/settings`(노트북 음성, 손 인식 설정)는 콘솔에 넣지 않았다.
- 1920×1080 전체 화면에서는 가운데 안내 칸 아래쪽 여백이 크다. 시연용으로 쓸 거면 반쪽(960×1080) 배치가 더 알맞다.
- 브라우저: Edge(Chromium)에서만 확인. `createImageBitmap`·CSS `aspect-ratio` 미디어 쿼리를 쓴다.
- HTTPS 자체 서명 인증서: 콘솔은 같은 출처 상대 경로만 쓰므로, 노트북 브라우저에서 `https://localhost:8460`의 인증서 경고를 한 번 넘기면 된다(미확인).

## 8. 2단계(실제 서버 연결) 때 확인할 것

1. `https://localhost:8460/admin/`이 열리고 `admin.css`·`admin.js`가 올바른 MIME(`text/css`, `text/javascript`)으로 오는지.
2. 머리줄 "서버 연결됨", 기록 구분 표시, "버튼 위치: 시연용 정답 좌표 사용".
3. 대기 중: 키오스크 `null`(연결 전) → "키오스크 연결 안 됨" 할 일 줄, 휴대폰 미연결 표시가 맞게 나오는지.
4. 시도 시작: `reset_kiosk` 기본값(true)으로 키오스크가 첫 화면으로 가는지, 조건이 `attempt_start`에 그대로 남는지.
